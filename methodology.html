Methodology

How G2 and Bluejay evaluate voice AI agent platforms: the environment every platform runs in, how the tasks were built, the exact definitions of task success, word error rate and latency, how models are chosen, and how the evaluation is kept fair.

1Overview

This document specifies how G2 and Bluejay evaluate voice AI agent platforms. The unit of evaluation is the platform: the hosted runtime that answers a call, decides when the caller has finished speaking, executes tool calls, and connects the speech-to-text, LLM and text-to-speech layers. The agent itself is held constant. Every platform hosts the same system prompt, greeting and tool schemas, takes the same simulated calls, and is graded by the same deterministic verifier, so a difference in outcome is a difference in how platforms run an agent.

The task suite and its environments are derived from the methodology described in MIVAS-Bench, Bluejay's benchmark of multi-step, tool-using voice agents.

1.1How platforms are graded

Each platform takes the same 630 simulated calls: 90 tasks run five times each, plus 36 copies of easy tasks under background noise or a degraded phone line, also run five times. Every call is graded by software, not by a person or a language model, and the results add up to a platform score out of 100:

80points

Task success

Did the agent do the job? A call passes only if our tool server's log shows every required tool called with the right details, and the business's database after the call matches the expected result. No partial credit.

80 × passes ÷ (450 − calls failed by a model we chose)

10points

Word error rate

Did the platform hear the caller? Its own transcript of the caller is compared with the caller's script: word errors, meaning-changing errors, and the names, dates and numbers it got right, on clean and on degraded audio.

10 × composite C, half clean, half degraded

10points

Latency

How long does the caller wait? Measured on our own recording, on every turn, from the end of the caller's speech to the start of the agent's reply.

Full at ≤ 1.0 s median and ≤ 2.0 s p95; zero at 4.0 s and 6.0 s

Failures that are not the platform's own do not count against it. Calls broken by our side (a task defect, a caller that left its script, a harness fault) are voided, fixed and re-run on every platform, and on platforms where Bluejay chose the speech or language models, failures caused by those models are reported separately rather than scored. §4 gives every formula, §7 how each failure is attributed, and a qualitative profile of each platform (§5) is reported beside the score without entering it.

2Evaluation environment

Every call runs in the same closed environment: a simulated business with its own database and tool API, a simulated caller, and the platform under test between them. Only the platform and its transport change from one run to the next.

2.1Simulated businesses

Each industry is a synthetic company with operating policies, a relational database and a tool API, modeled on a real deployment and on the rules that govern that kind of business:

Company identities, people and records are synthetic; the organizational boundaries and workflow constraints are the real ones.

2.2The agent under test

Each company's phone line was designed as a department of specialist agents (reception, identity, scheduling, billing and so on), each with production-length instructions and only the tools its role needs (Figure 2.2). Industry research came first: published agent deployments, operating policies, applicable regulation, call-centre request taxonomies and recurring failure cases from production evaluations, which together define what callers ask for and where an automated agent must defer to a person. The company, its workflows and its authorization gates were then specified from that research, and implemented as prompts, typed tools, a seeded database and server-side policy guards.

Workflow mapping assigned every kind of call to the specialist that owns it and encoded the authorization gates, decision points and escalation routes between them. The result is a different topology per industry: a privacy-gated, acyclic front desk in healthcare; a sequential admissibility funnel in legal; a cyclic service network for compound requests in customer support.

Most platforms run one agent per call, so each department is collapsed into a single agent for this evaluation: the specialists' instructions are merged into one system prompt (2,131 words in legal, 3,475 in healthcare, 3,523 in customer support), handoff tools are removed, and two session tools remain, transfer_to_human and end_call. Every business tool, the database and every expected end state are unchanged. The prompt, greeting and tool schemas are deployed byte-for-byte on every platform.

2.3Tool server and database state

Each industry has one tool server, and it is the only system of record. Every request carries the call's identifier. On the first request of a call the server creates a new SQLite file for that call from the industry's schema and seed, so every call begins from the identical state D0 and no call can observe another. Each subsequent tool call executes against that file, and every request is logged with its tool name, arguments, raw body, response, status and timestamps.

Platforms that run tool code inside their own runtime are configured with functions that forward each call to the same endpoint. At hangup the call's database is frozen. The verifier (§4.2) reads two things: the server's request log, which is what the agent actually did, and the frozen database, which is what it left behind. Neither depends on what the platform reports about itself.

2.4Simulated caller

Each caller is a Bluejay digital human configured from its task: an LLM-driven caller at temperature 0 that improvises phrasing but never facts. Its configuration has three parts. The intent states its goal and how it behaves. The traits are the facts it holds (name, phone, identifiers, dates) and the only values it may give. The scripted responses are trigger-and-line pairs: when the agent's turn matches a trigger, the caller says that line exactly, so every fact a task depends on reaches the agent in the same words on every platform and every run. A scenario clock fixes the date, so date arithmetic is identical across runs. Callers do not barge in.

Caller speech is synthesized by commercial TTS. Voices rotate over a fixed eight-slot list of accent and gender (American, mature and Southern; female and male) assigned by sorted task identifier, so a task has the same voice on every platform and every run, and its audio variants inherit it.

2.5Run protocol

A versioned manifest freezes the tasks, agent configuration, callers, voices, model pins (§6) and tool server build; any change creates a new version and every platform is re-run under it. The agent is deployed on the platform's production cloud in its default region, with turn-taking, interruption and timeout settings left at platform defaults. Each platform takes 90 tasks × 5 runs (450 scored calls) plus 36 audio variants × 5 runs (180 calls). Bluejay records every call in stereo, caller left and agent right; latency (§4.4) is measured on this recording, never on vendor-reported timings.

3Task suite

A task is one caller with one reason to call, the business behind the agent, and a fixed specification of what a correct resolution does to that business's systems.

Tasks were written against the agent graphs of §2.2, then run in full calls, inspected through their routing, tool traces and final state, and reviewed by hand. Each expected end state is generated by replaying the authorized tool sequence against a fresh seed rather than written by hand, so every expected state is reachable by construction. Before release each task ran ten times and every failure was attributed: 0% were task faults, 0% harness, 2% caller, and 98% model.

3.2The 90 scored tasks and their difficulty

Each industry has six categories of call, and each category contributes five tasks: one easy, two medium and two hard, for 30 per industry and 90 in total (18 easy, 36 medium, 36 hard). The set is fixed in the manifest and listed in full below.

Difficulty is a property of the workflow a correct resolution requires, not of how often models fail it. It is defined by four structural measures of the grading key: the number of expected tool calls; whether the work sits behind an identity or eligibility gate (verifying the caller, a conflict check, a practice-area or jurisdiction check); whether the call must change the database, and how many rows; and the number of constrained arguments the agent must get exactly right.

  • Easy. One request answered from public information or a single lookup. Usually no gate and no write. The agent must route correctly and not overreach.
  • Medium. Caller-specific work behind a gate: the agent must authenticate or screen the caller before it may read their records, and about half the tasks commit one change.
  • Hard. A multi-stage workflow that ends in a committed change, often a two-phase write (quote, read back, explicit confirmation, commit) with policy branches such as fees, proration or eligibility, and up to ten tool calls with up to sixteen constrained arguments.

3.3Audio conditions

An audio profile is a deterministic transform applied to the caller's synthesized speech before it reaches the platform. It is defined by a noise source and level, a codec chain with a bit-error rate, a packet-loss and jitter model, and a band limit. The caller's words, voice and expected end state are unchanged, so any difference in outcome is the platform's response to the signal. The easy task of each of the 18 categories is cloned under two profiles, giving 36 variants:

ProfileNoiseLineModels
CleanNoneWideband TTS audio, no impairmentA caller in a quiet room on a good connection
Background noiseRecorded road traffic, mixed into the caller's outbound audio at gain 0.8 (0.1 in legal, where 0.8 masked spoken ten-digit callback numbers)No impairmentA caller on the street
Degraded lineHiss and crackle (below)Narrowband mobile-to-landline path: codec tandem, bit errors, bursty loss, jitter, concealmentA weak mobile signal transcoded onto a landline network

The degraded line is built packet by packet on 8 kHz audio in 20 ms frames. Loss and jitter follow the ITU-T G.1050 network profiles; codecs follow the NISQA and NeMo telephony recipes. Losses are drawn from a two-state Gilbert–Elliott model, so they arrive in bursts rather than independently, and packets that arrive after the 60 ms jitter buffer are treated as lost:

Variants contribute the degraded-audio term of word error rate (§4.3). Their task success is reported separately and does not enter Stask, which is computed on the 450 clean calls.

4Metrics

All three components are computed by deterministic procedures from records Bluejay controls: the tool server, the call's database, the caller's script and Bluejay's own recording. No language model decides whether a call passed.

4.1Platform score

The platform score is the sum of three components, each computed by a fixed formula below. Half the points go to whether the job was done; the other half is split between the two things a caller notices first: being heard correctly and not being kept waiting.

4.2Task success

Let a task specify the expected multiset of tool calls T* and the expected final database state D*. Every call starts from the seed state D0. During the call the agent's tool calls apply a sequence of transactions τ1, …, τn to the call's database, and T is the multiset of calls the agent actually made:

D = τn ∘ ⋯ ∘ τ1(D0)
(2)

Tool adherence. 𝟙T = 1 if there is a one-to-one assignment of every expected call in T* to a distinct observed call in T with the same tool name and equal constrained arguments after normalization. Matching is order-free. Additional calls are permitted; the one forbidden pattern, an unrequested SMS in healthcare, fails the call. Constrained arguments are the ones that determine the outcome: identifiers, dates, enumerations, amounts and the industry's fact fields. Normalization folds phone numbers to digits, ignores case, spacing and typography, resolves documented aliases, accepts the alternatives a task lists, and matches party names by edit distance and phonetic similarity. Free-text arguments must be present but are not compared.

State adherence. 𝟙D = 1 if the call's final database equals the expected state on every write-bearing table, after projecting out volatile fields (creation timestamps, free text) and canonicalizing amounts, payment methods, phone numbers and datetimes. Tables that act as append-only logs (notes, messages, documents) are compared as a subset; all others must match exactly. State adherence is what catches an agent that says the right thing but writes the wrong record, or writes nothing at all.

pass(c) = 𝟙T(c) · 𝟙D(c)
(3)

There is no partial credit. A call that breaks (dropped audio, an error prompt, no agent speech, or a tool request that never reaches the server) is a failure. Every failed call is then attributed to one cause (§7.2). A call that failed because of a model Bluejay selected for the platform under §6 is left out of the task score, because the platform did not choose that model; a failure caused by a model the platform bundles, recommends or ships as its flagship is the platform's, because that model is part of the product. With N = 450 clean scored calls, P the passes and FM the failures attributed to a Bluejay-selected model:

Stask = 50 · p,    p = P / (N − FM),   N = 450
(4)

The raw pass rate P / N and the number of failures attributed to each selected model are published beside the score, so the effect of the exclusion is visible.

Because each task runs k = 5 times, consistency is also reported as pass5, the share of tasks that pass on all five runs. It does not enter the score.

4.3Word error rate

The reference r is the caller's text exactly as it was sent to the caller's TTS; the hypothesis h is the platform's own final speech-to-text output for the caller. Reference utterances and hypothesis lines are first aligned by sentence-embedding similarity, so differences in how turns are segmented are not errors, then word by word. Three rates are pooled over calls:

  • WER = (S + D + I) / Nr: substituted, deleted and inserted words over reference words, capped at 1.
  • SWER: the same alignment, but a substituted phrase that keeps the meaning (cosine ≥ 0.75, or confirmed by an LLM judge between 0.55 and 0.75) is not an error.
  • FFA, form-filling accuracy: of the names, dates, numbers and identifiers the caller says that the task needs in a tool call, the share present in the platform's transcript.
C = ⅓ [ (1 − WER) + (1 − SWER) + FFA ],   SWER = 25 · ( ½ Cclean + ½ Cdegraded )
(5)

Cclean pools the 450 clean calls and Cdegraded the 180 variant calls. The composite is computed on every completed call whatever its grade, so how well a platform hears always reaches its score.

The synthesis floor. The reference is the text the caller's TTS was asked to say, not the audio it produced. If the TTS mispronounces or drops a word, a platform that transcribes the audio faithfully is charged an error it could not avoid, so measured WER ≈ WERplatform + ε, where ε is the synthesis error of the caller voices. ε is identical for all platforms and cannot change their order; it is estimated per voice with an independent reference ASR and published with the results.

4.4Latency

Latency is the time the caller waits. For each caller turn i it is the interval from the end of the caller's speech to the onset of the agent's reply, measured on Bluejay's stereo recording:

ℓi = tagent onset, i − tcaller end, i
(6)

The caller's end is the last voiced frame of the caller channel within ±1.5 s of the transcript's end of utterance. The agent's onset is the first 50 ms window on the agent channel whose energy exceeds four times the channel's 20th-percentile RMS, before the caller's next utterance. Turns in which the agent is already speaking when the caller finishes are excluded. Turns with tool calls are included, because the caller waits through them. Turns are pooled over all scored calls; m is the median and q the 95th percentile:

Slat = 25 · [ 0.6 · clip((4 − m) / 3) + 0.4 · clip((6 − q) / 4) ]
(7)

The median term is full at 1.0 s and zero at 4.0 s; the tail term is full at 2.0 s and zero at 6.0 s. The tail carries 40% of the weight because a caller experiences the slowest turns of a call, not its average. Measuring on our own recording applies one method to every platform, including platforms that expose no timing data, and includes everything the caller hears: endpointing, inference, synthesis and transport.

4.5Precision

The pass rate is a proportion over N = 450 calls, reported with its 95% Wilson interval. The interval's half-width is at most 4.6 percentage points, or 2.3 points of Stask. Platforms whose intervals overlap on a component are reported as tied on it.

5Platform profile

The platform score measures how well a platform runs a fixed agent. It does not measure what it takes to build that agent, take it to production and operate it, which is much of what a buyer is choosing between. Each platform is therefore also profiled in eight categories. The profile is reported on each platform's page and does not enter the platform score.

5.1Grading

Each category is a set of features with weights summing to 10. Each feature is graded full (1), half (0.5) or none (0) and multiplied by its weight. Every grade cites its evidence: a vendor document with its URL and the date it was read, an API response, or a Bluejay recording. Five features are measured rather than read: time to first agent (stopwatch), interruption handling (probe calls on platform defaults), runtime under load (break rate at 20 concurrent calls against the 2-call baseline), cost per hour (our estimate from public pricing against the actual bill for the scored calls) and language support (one probe task per language). A feature graded by judgment before its measurement exists is marked with an asterisk until the measurement replaces it.

6Model configuration

Where a platform lets the builder choose a model, the choice is made by a fixed rule, independently for each layer and each platform, from the models that platform can run. Bundled models are used as shipped; otherwise a platform's documented recommendation; otherwise its newest flagship. The remaining open-choice layers (LiveKit Agents and Pipecat) use the rule below. Rule, data and result were frozen on 27 Oct 2026 in manifest v5.

Each open-choice layer scores its candidates on two metrics a and b, each min–max scaled over the candidate set so that 0 is the best value and 1 the worst. The selected model minimizes the equal-weight sum over the Pareto frontier F, among models that are generally available, run on the platform, and accept their exact identifier on a live call:

s(m) = ½ a′m + ½ b′m,   x′ = (x − xbest) / (xworst − xbest),   m* = argminm ∈ F s(m)
(8)

For the LLM, a and b are the Artificial Analysis Intelligence Index q and time to first answer token ℓ. Because ℓ ranges from under a second to minutes across reasoning settings, candidates are first restricted to ℓ ≤ ℓmax, the slowest first token at which a tool-call turn (two LLM passes, a tool round trip r and the measured speech overhead o) still reaches the caller before the 4.0 s zero point of §4.4:

ℓmax = (4.0 − o − r) / 2 = (4.0 − 1.33 − 0.25) / 2 = 1.21 s
(9)

7Validity and fairness

A comparison between platforms is fair if every difference in their scores is caused by the platforms. Formally, let κ(c) be the cause of a failed call c. The evaluation is fair when every failure that enters the score has κ(c) in the platform's own stack, and every failure caused by Bluejay (a wrong task, a caller that left its script, or a harness fault) is removed from every platform's results and re-run, so that all platforms are scored on the same 450 calls under the same conditions. This section describes how the conditions are held equal, how each failure is attributed, and how our own defects are found before results are published.

7.1Conditions held equal

ConditionControl
InputsIdentical agent, tasks, caller scripts, voices, seed state and tool server for every platform, frozen in the manifest. Any change to any of them re-runs every platform.
GraderDeterministic tool and state diffs, WER and latency, computed by one verifier version for all platforms. No language model decides whether a call passed, so there is no judge to calibrate or to drift.
CallerCallers at temperature 0, with every graded fact and decision fixed by scripted responses; five runs per task; every call recorded in stereo.
ModelsChosen per platform by the rule in §6 from models that platform can run, frozen, and published. Failures of a model Bluejay selected are not counted against the platform (§7.2).
SettingsNo platform-specific prompt changes. Turn-taking, interruption and timeout settings stay at platform defaults.
Run conditionsCallers originate from one cloud region; concurrency is fixed per platform at its entry-level limit and published; latency is measured on our recording with one method.

7.2What counts against a platform

Every failed call is assigned exactly one cause, from the evidence of §7.4, checked in this order; the first that applies is recorded:

#CauseTestCounts against the platform
4PlatformTurn-taking, interruption handling, tool execution or session handling failed: the agent was cut off, a tool request never reached the server, or the session droppedAlways
5Speech-to-textA detail the task needed (a name, date, number or identifier) is wrong in the platform's transcript of the caller, and the caller's audio carried itWhen the platform chose the model
6LLMThe transcript was correct, but the agent chose the wrong tool or argument, skipped a required step, broke a policy gate, or stated something the tools did not returnWhen the platform chose the model
7Text-to-speechThe agent's reply was correct in text, but its audio did not carry it to the callerWhen the platform chose the model

The order matters. A wrong decision made on a misheard transcript is a speech-to-text failure, not an LLM failure, so speech-to-text is checked before the LLM. Causes 5 to 7 depend on who chose the model. Where the platform bundles, recommends or ships the model as its flagship, the model is part of the product and its failures are the platform's. Where Bluejay selected the model under §6 (LiveKit Agents and Pipecat), its failures are attributed to the model, left out of the task score of equation (4), and published separately, so an open framework is not penalized for a model we chose and a closed platform is not credited for a model it chose. Every other failure (a task whose specification or expected state is wrong or ambiguous, a caller that deviated from its script, or a fault in our tool server, transport bridge or recording) is Bluejay's, is never scored, and is handled by §7.3 and §7.4.

7.3Voids and re-runs

Before grading, each call is checked against four void rules. A voided call is not a pass or a failure; it is re-run until every task has exactly five graded runs on every platform. A call that connected but broke (dropped audio, an error prompt, a tool request that never reached the server) is not voided: it is a platform failure.

VoidCondition
Refused or cancelledThe platform never accepted the call, or the run was cancelled before it connected
No agentThe call ended before the agent produced any speech
PhantomA result was recorded with no audio and no transcript: nobody spoke
Caller left firstThe caller hung up before giving a reason and no tool was called; not applied to degraded-audio variants, where an agent that never heard the caller has failed

7.4Finding our own defects

A deterministic grader is only as fair as the tasks and callers it grades. Four procedures find defects on our side, and every one runs on every platform:

  • Live tracking. During each run, every result is compared with its task as it arrives. A failure pattern that repeats across runs or platforms is raised immediately, with result identifiers, rather than discovered after grading.
  • Stratified fairness audit. After each run, a seeded 25% sample of the platform's calls is drawn, stratified by industry and task family so every kind of call is represented. A reviewer attributes every failed call in the sample by reading the recording, the transcript, the tool server's request log and the database diff, and spot-checks a seeded sample of passing calls for false passes.
  • Cross-platform comparison. Each task's pass rate is compared across platforms. A task that fails the same way on platforms with different stacks is reviewed as a suspected task or caller defect; a task that fails on one platform and passes on the others is evidence that it is passable.
  • Exhaustive review of hard failures. Every task that fails all five runs on any platform is reviewed in full.

A confirmed defect is fixed once, for every platform. A fix to the grading key (for example, an expected call the agent's prompt never asks for) is applied by re-grading every platform's stored calls without new calls; a fix to a caller script (for example, an opening line that omitted the date the task depends on, or a caller with no line for accepting an offered transfer) requires new calls on every platform. A fix is never applied to one platform alone. Before any change to the grader is accepted, it must reproduce every previously graded outcome except the ones it is meant to change.

Grader normalization is deliberately lenient where the agent cannot be expected to be exact (spacing, case, number formats, documented aliases, phonetic name matching). Leniency can let a near-miss pass, but it applies identically to every platform, so it cannot change their order.

7.5Human review and right of reply

Before results are published, each platform receives its results, the recordings of its failed calls and their attribution, and may flag factual errors. A flagged call is re-reviewed; a confirmed Bluejay defect is fixed and re-run on every platform.

7.6Reproducibility

For every call Bluejay retains the manifest version, the platform and pinned stack, task and run number, audio condition and caller voice, the stereo recording, the platform's transcript, the tool server's request log, the final database, per-turn timings, and the grade with its cause. Anyone holding the manifest and configuration files can redeploy the agent on a platform and re-run any task.

7.7Limitations

  • The suite is English-only and covers three industries. Results may not transfer to other languages, caller populations or workloads.
  • Callers are simulated. Their speech is synthetic, so measured WER includes the synthesis floor ε of §4.3, and they do not reproduce every behavior of human callers.
  • The degraded-line profile is severe enough that parts of the caller's speech are hard to recover even for a reference transcriber. Its results are reported separately from task success.
  • Calls originate from one region over each platform's standard transport; carrier and PSTN conditions beyond the degraded-line profile are not covered.
  • Results describe each platform and pinned stack on the run date. Platforms and models change, and each round is versioned.
  • The profile (§5) records documented capabilities, and some features involve judgment until measured; it is therefore kept out of the platform score.
